# ADR 0001：保留两种开发模式，先明确接口合同

状态：本轮文档采用；业务架构迁移未实施。日期：2026-11-08。

## 问题

团队需要快速接手旧页面，又不能把遗留风险复制到新功能。按 Area 猜数据库、统一替换写接口或绕过代理，会破坏现有合同。

## 证据

工作流证据 R01/R02 显示 VIP 动态视图解析；R03/R04/R28/R29 描述接口到连接的映射；R20/R21/R22 显示动态 flag 与无 @result 的结果集命令；R24/R25/R30 显示 Proxy 与真实 WebApi 编译源。

## 采用的方案与依据

- 保留通用存储过程和 WebApi + Proxy 两种模式，按已有模块及业务边界选用，减少一次迁移造成的兼容风险。
- 将过程名、flag、参数、结果形状、成功值、身份来源写成可验证合同，防止 AI 从单一成功示例推导全站规则。
- IT 与 Agent 共用同一正文，减少两套规范漂移；个人路径独立配置，源码证据使用相对路径。
- 先修可信身份、文件边界和错误传播，再推进共享组件和模块拆分，优先解决已有可追溯风险。

## 暂不采用

不全站重写前端、不统一将写入改成 PostString、不把 Host.Modules 生成副本作为主实现、不把所有审查建议立即改成代码。当前没有运行数据支持这些投入。

## 代价与待验证假设

两种模式继续并存会增加学习成本，因此必须维护合同表。生产 SQL 与仓库 SQL 可能不一致；代理后的直接 API 访问控制也需独立核实。当前仅有静态证据，不能认定所有安全修复路径已经完成设计。

## 何时重新评估

至少一个 SI/EAP 和一个 Proxy 模块完成正常、失败、权限、并发与回退验收后，依据复用收益和实际缺陷决定是否提取共享适配层。
